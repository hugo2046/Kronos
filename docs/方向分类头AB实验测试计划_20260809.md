## 2. 阶段 1：配置准备

现有 `finetune_csv/configs/config_classifier_ali09988.yaml` 是模板，有两处**必须改**：
`data_path` 写死了 macOS 路径 `/Users/hugo/...`；`paths.pretrained_*` 为空（方案 B 会直接 `ValueError`）。

`train_classifier.py` 只接受 `--config`，**没有** `--backbone`/`--data_path` 覆盖参数，
所以拆成两份配置文件，而不是来回改同一份（防止两次实验的配置无法追溯）：

- `finetune_csv/configs/config_classifier_ali09988_A.yaml`
  - `data.data_path: /home/user/workspace/Kronos/finetune_csv/data/HK_ali_09988_kline_5min_all.csv`
  - `classifier.backbone: from_scratch`
- `finetune_csv/configs/config_classifier_ali09988_B.yaml`
  - 同上 `data_path`
  - `classifier.backbone: pretrained_probe`
  - `classifier.paths.pretrained_tokenizer: "NeoQuasar/Kronos-Tokenizer-base"`
  - `classifier.paths.pretrained_predictor: "NeoQuasar/Kronos-base"`

**除以上字段外，两份配置必须逐字节相同**（同 seed=42、同 lr、同 batch_size、同早停策略、
同 quantile 阈值），否则对照实验不成立。

**验证标准**：`diff` 两份配置，差异行数恰好为上述 4 行 + 注释。

## 3. 阶段 2：方案 A（从头训练）

```bash
/home/user/miniconda3/envs/quant/bin/python finetune_csv/train_classifier.py \
  --config finetune_csv/configs/config_classifier_ali09988_A.yaml \
  2>&1 | tee finetune_csv/finetuned/classifier/log_A.txt
```

（`train()` 返回的 results 字典在 `main()` 中被丢弃、不落盘，**日志是唯一产物**，`tee` 不可省。
`finetuned/classifier/` 目录尚不存在，先 `mkdir -p`。）

**过程中要核对的中间量**（这些是数据管线正确性的体检指标，异常即停）：

1. `[TRAIN]/[VAL]/[TEST] 时间范围` 三段**严格递增且不重叠**——确认是时序划分而非随机划分；
2. `[TRAIN] 阈值分位数估计：low=..., high=...`，low < 0 < high，量级应在 1e-3 ~ 1e-2；
3. 三段 `可用样本` 数约为 `段长 - 99`（L=90, H=10），train 段应在 6.5 万左右；
4. `class_weights` 三个值——quantile 30/70 分箱下 train 集类别接近 3:4:3，权重应都在 1 附近；
   若某一权重畸大（如 >5），说明分箱退化，需先排查再继续；
5. 首个 epoch 的 `val_macroF1`——若恒等于 0.1667（= 只预测单一类的 macro-F1 上界附近）
   且多轮不动，属不收敛，转 `superpowers:systematic-debugging`，不要盲目调参。

**成功标准**：跑完 30 epoch 或触发早停，打印出测试集 accuracy / macro-F1 / 混淆矩阵、
双基线对比表、金融口径三行，且 `finetune_csv/finetuned/classifier/best_from_scratch.pt` 存在。

## 4. 阶段 3：方案 B（冻结主干 linear probe）

**先做 1 epoch 计时探针**：临时把配置的 `training.epochs` 改成 1 跑一遍，记录单 epoch 墙钟时间。
方案 B 每步要过冻结的 Tokenizer + 12 层 832 维主干（约 97.5M 参数），
比方案 A 的 0.68M 慢一个量级以上。若单 epoch > 20 分钟，先把 `batch_size` 提到 128
（5090 有 32GB 显存，冻结主干无梯度，显存压力主要来自激活）再跑全量——
**此时方案 A 必须用同样的 batch_size 重跑**，否则破坏对照。

全量运行：

```bash
/home/user/miniconda3/envs/quant/bin/python finetune_csv/train_classifier.py \
  --config finetune_csv/configs/config_classifier_ali09988_B.yaml \
  2>&1 | tee finetune_csv/finetuned/classifier/log_B.txt
```

**方案 B 特有的核对项**：

1. 日志出现 `加载预训练 Tokenizer/Predictor` 两行 + HF 下载进度（首次约百兆）——
   **没有这两行就说明走错了分支**；
2. `模型参数：X（可训练 Y）`，Y 必须 ≈ `d_model × 3 + 3` = 2499（只有 probe），
   X 约 1 亿量级。**Y 若是 X 说明冻结失效**，立即停止；
3. 每轮保存全量 `state_dict`（含 97.5M 冻结参数，约 400MB/次），
   确认磁盘余量 > 5GB；这是已知遗留问题，本次不修，只做规避。

**成功标准**：同阶段 2，产物为 `best_pretrained_probe.pt` 与 `log_B.txt`。

## 5. 阶段 4：结果判读

把两份日志的末段汇成一张表：

| 方法 | accuracy | macro-F1 | 平均每步收益 | 胜率 |
|---|---|---|---|---|
| 多数类基线 | | | — | — |
| 动量基线 | | | — | — |
| 方案 A from_scratch | | | | |
| 方案 B pretrained_probe | | | | |

**判读规则（按顺序，先判否决项）**：

1. **否决项优先**：若 A、B 的 macro-F1 **都**不高于多数类基线与动量基线中的较大者，
   结论是"该标的数据量不足以支撑单标的择时分类路线"——按交接说明 §3 与方案文档 §6.2，
   应转向东证报告推荐的截面因子路径，**不要继续调参**。调参在没跑赢朴素基线时是纯过拟合。
2. 若 B 显著优于 A（macro-F1 差距 > 0.02），即"预训练红利不可丢"的直接证据，
   与东证报告结论互相印证，应记录并推荐 probe 路线。
3. 若 A ≥ B，需谨慎——这与论文口径相悖，先检查方案 B 是否真的加载了预训练权重
   （回看阶段 3 的核对项 1、2），排除加载失败后才可下结论。
4. **不要单看 accuracy**。三分类下多数类基线的 accuracy 可以很高而 macro-F1 很低，
   脚本已内置 `⚠` 警示行，日志里出现就必须在结论里如实写出。
5. 金融口径的 `mean_period_return` 实为算术平均而非时序复合（已知命名口径问题），
   写结论时按"平均每步收益"表述，不要说成"累计收益"。
