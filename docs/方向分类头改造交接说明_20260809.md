## 3. 接手第一步：跑通 A/B 对照实验

1. 复制 `finetune_csv/configs/config_classifier_ali09988.yaml`，填入真实 CSV 数据路径；
2. **方案 B** 需在 config 填 `pretrained_tokenizer: "NeoQuasar/Kronos-Tokenizer-base"`、`pretrained_predictor: "NeoQuasar/Kronos-base"`（首次运行会从 HuggingFace 下载约百兆权重；路径留空会直接 `ValueError`，这是刻意设计，不要绕过）；
3. 分别以 `backbone: from_scratch` 与 `backbone: pretrained_probe` 各跑一轮，对比 val/test 的 macro-F1 与双基线结果；
4. **判读标准**：若方案 B 显著优于方案 A，即为"预训练红利不可丢"的直接证据，与东方证券报告结论相互印证（见方案文档 §6.2）；若两者都战胜不了多数类/动量基线，说明该标的数据量不足以支撑此路线，应转向报告推荐的截面因子路径而非继续调参。

## 5. 已知遗留（均不阻塞，按需处理）

- `mean_period_return` 命名口径（实为算术平均，非时序复合）；`win_rate` 与其分母基数不同但返回值未说明；
- `_rate_to_label` 是私有方法却被 `train_classifier.py` 跨模块调用——建议提升为公共接口（基线与标签共享分箱口径是设计意图，值得公开）；
- `ClassifierConfig.num_workers` 是死配置（DataLoader 未传该参数）；每轮保存全量 `state_dict`，方案 B 下会反复写盘约 97.5M 冻结参数；
- **仓库既有 bug（本分支刻意未动）**：`finetune_csv/finetune_base_model.py:125` 的 `CustomKlineDataset` 用整窗口（含未来段）统计量做 z-score，偏离论文"仅回看窗口"的规定，对现有生成式微调同样是泄露。建议另开 issue 单独修复。
